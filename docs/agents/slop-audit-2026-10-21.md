# Codebase slop audit, 2026-10-21

## Review summary

The audit found more value in fixing ownership, ordering, and trust boundaries than in removing small abstractions. The most serious findings let client profile text select another person's content, grant admin authority from an unverified email, or allow an AI refund to race paid output publication. The implementation also fixes stale wallet balances, pagination cursors, session repairs, moderation actions, and follow intents.

Cleanup stays narrow. Proven dead or test-only convenience methods are removed, and their useful tests now call live APIs. Source-spelling checks and a false shader compilation claim are removed without deleting real platform, resource, rendering, or cross-language contract coverage. There is no general rewrite of dynamic maps, repository layers, native bridges, or generated code.

All implementation handoffs are complete. Final integration checks and independent reviews are recorded below. Local fixes do not authorize production rollout. Favourite aggregation must not start with an empty contribution ledger against already-counted favourites. A gated, dry-run-first bootstrap must preserve existing membership before the new trigger serves traffic. No migration has run. Real iOS release configuration is absent, and no device or live-production proof is claimed.

## Recurring patterns

| Pattern | Concrete examples | Fix applied |
| --- | --- | --- |
| Trusting client identity or stale authorization | Profile email used by deletion, unverified email-based admin access, permissive follower edits | Bind authority to verified Auth identity and exact allowed mutations. |
| Async work without ownership | Follow queues, sign-in rollback, profile/cache loads, ads, native mirrors | Capture the owner and operation generation, then check after awaits and before publication. Serialize writes where order matters. |
| Duplicated or lossy state | Client coin subtraction, category replaced by description, missing notification kind, empty collection refresh | Preserve authoritative balances and typed meaning across live state, persistence, and mapping. |
| Non-atomic side effects | AI cancellation/publication, favourite totals/daily counters/quest rewards, initial username claims | Put competing decisions in the same transaction and retain durable retry work where a second transaction is necessary. |
| Dead convenience APIs | Test-only persistence wrappers, Dart icon wrapper, Android formatter, Swift error case | Trace all consumers, remove unused entrypoints, and keep registered/native/generated contracts. |
| Tests tied to implementation spelling | Kotlin source strings, false shader compilation assertion, mock detection in production | Assert observable behavior, actual platform contracts, and persisted results. Keep real browser and emulator checks scheduled in CI. |
| Tooling that works only in one environment | Shell-expanded release arguments, absent Firebase release config, backend-only contract gaps | Pass argument arrays directly, validate real configuration before signing, and run cross-language contracts for the relevant changes. |

## Rollout constraints and unexecuted operations

These are required ordering constraints, not instructions already executed. Every production deploy, rule change affecting installed clients, data apply, secret provisioning, or store upload needs the user's explicit approval at the concrete step.

### AI charge protocol

1. Pause paid AI generation/refund traffic and drain old callable and Worker invocations. Waiting only for a claim to become stale is insufficient because the old Worker lacks the final commit/publication fence.
2. Deploy the new refund callable first and retire/drain old revisions. Against an old Worker without the cancellation route, AI refunds fail closed rather than credit from read-only status. Non-AI download refunds keep their independent policy.
3. Deploy Worker and Durable Object protocol together. Preserve the coordinator namespace and `AI_REQUIRE_CHARGE=true`. Verify token forwarding and caller-owned receipt access before reopening traffic. A callable-only rollback is unsafe.
4. Reconcile legacy ownerless coordinator records through trusted ledger/provider evidence under a separately approved plan. Do not guess UID ownership, bulk adopt/delete records, or silently refund them. New code intentionally rejects automatic replay/cancellation for ownerless records.
5. Verify paid success/replay, failure cancellation/refund, pending denial, and lost-ack recovery outside production before reopening. Already-published old output cannot be recalled by this fix.

Cancellation and Firestore credit are not one distributed transaction. Cancellation remains terminal and retryable if credit aborts. A later refund request can finish the credit without reopening generation. Private staged output has a 24-hour TTL, and post-commit KV/R2 publication can still fail or expire. Owner replay retries while staging/coordinator state remains available. Prolonged loss needs operational reconciliation, not automatic refund after committed success.

### Identity and installed clients

The reservation callable/creation/deletion logic must be available before the migrated app. The creation trigger accepts legacy initial-name candidates for server-first compatibility, but tightened rules reject old clients' direct canonical username writes. Coordinate rules approval with installed-client adoption or an explicit compatibility plan. Backend-first alone does not close bypasses while permissive old rules remain, and immediate rule tightening can break old editor/sign-in flows.

The chosen username policy is reuse after deletion. Future deletion and guarded historical on-demand reclaim implement that choice. Reclaim requires `deleted: true`; missing, malformed, unknown, or active prior owners stay blocked. No bulk username migration occurred. Existing duplicate/unreserved names and forged historical profile data were not repaired automatically. Verify real Google/Apple email spelling and verification semantics in staging, including email-less identities and denied unverified email-based author/follower/admin actions.

Favourite rules preserve valid Prism/WOTD/Pexels/Wallhaven writes with matching path IDs. Unsupported/malformed legacy data remains readable/deletable, but guest imports trying to rewrite it may fail. Do not silently weaken identity rules to accommodate unknown providers. Plan that compatibility explicitly.

### Favourite ledger bootstrap

SV-S08 cannot be released as only a new trigger. Existing aggregates already count historical favourites, while an empty contribution ledger would treat those memberships as new. That creates new drift on the first retry. Documentation of this risk alone is not a fix.

The updated backend handoff adds [backfillFavouriteContributions.ts](../../functions/src/backfillFavouriteContributions.ts) and a [package script](../../functions/package.json), with a [maintenance gate in wallStats](../../functions/src/wallStats.ts). It uses a stable epoch and resumable scanning/publishing phases. Aggregation refuses work until the gate is `ready`. Parent review, build, unit tests, and emulator tests pass. These checks do not authorize running the tool against production.

The tool defaults to dry run with `cd functions && npm run migrate:favourite-contributions`. Each invocation scans at most ten pages of 100 image documents by default. `-- --cursor=<full-document-path>` continues a dry run, and `--max-pages=N` adjusts its bound. Apply requires the separately approved `--apply --epoch=<stable-run-id> --confirm-favourites-frozen` arguments and repeated calls with that same epoch until the tool reports `phase: ready`. No command in this paragraph was executed for this report.

The final approved rollout must satisfy these conditions:

1. Complete a bounded, paginated dry run first. Review totals, aliases, malformed/external rows, cursors, and read/write cost. A partial page's unique-pair count is not a complete global inventory.
2. Freeze favourite writes through an enforceable mechanism and drain old aggregation/quest invocations. A CLI confirmation flag alone does not enforce the freeze. Keep writes frozen through scan, publish, verification, and protocol cutover so no transition falls between the old aggregate and new ledger.
3. With separate approval, backfill one active contribution per live UID/canonical wall and initialize matching aggregate totals. Preserve existing valid counts by representing historical memberships before live processing. Any intentional correction of pre-existing alias/count drift must be visible in the reviewed dry-run comparison, not an unexplained reset to zero or a fresh increment of already-counted favourites.
4. Make apply resumable/idempotent under a stable epoch. Bound pages, verify checkpoints cannot move backward, do not emit historical daily/quest rewards, and do not expose a half-published state as ready.
5. Verify legacy-count preservation, first post-bootstrap create/delete/retry, aliases, stale deliveries, transaction failures, durable pending quest recovery, and day rollover. Compare ledger membership and aggregates before enabling the final gate and unfreezing writes.
6. Keep the freeze/gate/trigger/rules cutover coordinated and have a recovery plan for interrupted publishing. Do not deploy the ungated earlier design or run apply while ordinary writes continue.

Bootstrap scans the `images` collection group using full-document-path checkpoints, including orphan subcollections, and filters unrelated paths. It deduplicates aliases into one active UID/canonical-wall contribution, then publishes absolute totals for every stats document, including zero when no live memberships remain. It preserves non-favourite stats and does not replay historical daily/quest awards. Resuming a partially published page is safe only while the original write freeze remains intact.
